# 运维手册

## 一、日常操作

全部在管理后台完成（也可用 API，见 [SDK接入指南](SDK接入指南.md) 末尾的管理 API 一节）：

| 操作 | 说明 |
|---|---|
| 发卡 | 「发卡」页：类型/数量/每卡设备数/前缀/备注，生成后一键复制发货 |
| 封禁 / 解封 | 「卡密」页单行操作或勾选批量；封禁 = 临时停用可逆 |
| 解绑 | 客户换机时解绑旧设备（单卡或批量） |
| 续期 | 给已激活的卡 +N 天（永久卡无需续期） |
| 删除 | 彻底作废（连设备绑定清除，不可恢复），仅用于彻底废弃 |
| 搜索 | 卡密 / 备注 / 设备号模糊搜索 + 状态筛选 |
| 应用管理 | 新建应用 / 停用 / 换密钥 / 复制密钥 |

## 二、多应用管理（N 个软件共用一台服务器）

1. 「应用」页新建应用 → 自动生成独立 ks/gk
2. 各软件客户端分别集成自己应用的 ks/gk
3. 卡密跨应用互不识别（A 卡在 B 应用客户端返回"不存在"）
4. 应用停用：该应用所有验证立即 403
5. 换密钥（rotate）：该应用旧客户端全部失效，需重新打包分发

## 三、改密钥 / 端口流程（两端必须同步）

涉及 `config.json`：`port` / `ks` / `gk` / `admin_token` / `session_secret`。

1. 改服务器 `config.json`
2. `systemctl restart card-server && curl http://127.0.0.1:8080/health`
3. 同步客户端侧的 ks/gk/server 地址，重新分发
4. 旧客户端在宽限期内仍可用缓存，之后失效

> 注意：多应用场景下 ks/gk（默认应用）只影响引导应用；各应用独立换钥走后台 rotate。

## 四、备份与恢复

```bash
# 手动备份
cp data.db backups/data-manual-$(date +%m%d).db
# 恢复
systemctl stop card-server
cp backups/data-XXXX.db data.db
systemctl start card-server
```

每日首次启动自动备份到 `backups/`，保留最近 7 份。

## 五、故障排查

| 现象 | 处理 |
|---|---|
| `curl /health` 不通 | `systemctl status card-server`；端口被占用改 config.json |
| 客户端提示"响应校验失败" | 客户端 gk 与服务端不一致；核对两端配置 |
| 客户端提示"无法连接" | 服务器宕机 / 安全组未放行；48h 宽限内客户端走缓存 |
| 验证一直"卡密不存在" | 确认卡属于该应用（多应用隔离）；确认卡号前缀格式正确 |
| 管理后台登录失败 10 次 | 锁定 10 分钟后自动解锁，或重启服务清零 |

## 六、安全建议

- `config.json` 含全部密钥，**不要提交到公开仓库**（本仓库已用 .gitignore 排除）
- 管理后台建议只走 HTTPS 反代或 SSH 隧道访问
- 定期轮换 ks/gk（尤其怀疑泄露时）
- 服务器只开放必要端口；数据目录定期异地备份
